# 安全规范
系统整体的安全规范以[等保2.0](https://openstd.samr.gov.cn/bzgk/gb/newGbInfo?hcno=BAFB47E8874764186BDB7865E8344DAF)作为目标,在系统应用层面做防护。

## 信息化系统安全相关概念(不重要，可跳过)
### 等级保护
等级保护是指对国家重要信息、法人和其他组织及公民的专有信息以及公开信息和存储、传输、处理这些信息的信息系统分等级实行安全保护，对信息系统中使用的信息安全产品实行按等级管理，对信息系统中发生的信息安全事件分等级响应、处置。
根据[信息安全技术 网络安全等级保护定级指南GB/T 22240-2020](https://openstd.samr.gov.cn/bzgk/gb/newGbInfo?hcno=63B89FFF7CC97EBBBED8A403396F0F00),据系统遭到破坏后对国家安全、社会秩序、公共利益以及公民、法人和其他组织的合法权益的危害程度等，由低到高一共5个等级。
- 第一级，等级保护对象受到破坏后，会对相关公民、法人和其他组织的合法权益造成损害，但不危害国家安全、社会秩序和公共利益；
- 第二级，等级保护对象受到破坏后，会对相关公民、法人和其他组织的合法权益造成严重损害或特别严重损害，或者对社会秩序和公共利益造成危害，但不危害国家安全；
- 第三级，等级保护对象受到破坏后，会对社会秩序和公共利益造成严重危害，或者对国家安全 造成危害；
- 第四级，等级保护对象受到破坏后，会对社会秩序和公共利益造成特别严重危害，或者对国家 安全造成严重危害； 
- 第五级，等级保护对象受到破坏后，会对国家安全造成特别严重危害。

信息化系统，特别是政府和国企相关的系统，等保是一个绕不过去的内容，相关的信息化部门都会有所要求。
等级保护定级，是评定专家根据上述内容做定级，一般常见的是第二级和第三级，也就是常说等保二级和等保三级。 具体评定和评测可以看[【网络安全】什么是“等保2.0”？看完这十个问题你就明白了](https://mp.weixin.qq.com/s?__biz=MzA5MTIwMzAxMw==&mid=2652436730&idx=1&sn=89475d10e396b84eb6059a647ed08dbd&chksm=8b93ac50bce42546a8f2e17ecef0cf72a1960f8f5d8763675175463140120514ac552c3e06d2&scene=27)
要求主要分为配套制度和技术要求，技术要求又分为物理、网络、应用和数据等层面，系统只从应用和数据层面做安全规范约束 。

*等保的评定工作一般会有评测公司(付费)协助完成，按评测公司的要求准备材料和完成系统安全问题处理即可，不需过多担心*

### 漏洞扫描和安全报告
信息化系统，在生产环境部署后，信息化部门经常会利用漏洞扫描软件(如明鉴)做系统的漏洞扫描，并出具安全报告。
按照安全报告的内容和要求做整改即可，一般漏洞会出在操作系统、数据库、各种中间件、应用三方包的CVE，系统的防火墙等安全策略，尽量避免被发现系统应用层面人为逻辑漏洞引起安全问题。
应对措施，事前及时检查操作系统、数据库、各种中间件的安全漏洞，及时更新版本或者打补丁，对安全策略做严格控制；事后根据报告及时按要求整改。

### 安全通报
除了自主的漏洞安全扫描外，部分城市的网信办等部门也会对互联网上暴露的系统做安全漏洞扫描，被发现后会给系统持有人发送网络安全预警通报，要求做整改。

## 常见的安全问题及解决办法
### 操作系统和数据库等中间件安全漏洞
描述：操作系统、数据库、nginx等中间件，会有CVE安全漏洞，会被要求整改
解决办法：开发选型阶段尽量选择安全稳定的(其实都一样，都会爆安全漏洞)，以及版本尽量选较新版本；运维期间适度升级版本打补丁(谨慎，很容易因为升级出问题)；被通报漏洞后，及时修复补丁。

### 安全策略层面
服务器交付使用后，一般会限制端口访问等网络策略，服务器自身防火墙也可以做自我限制。           
使用最小原则，也就是只申请必须的访问策略，非必须的一律不申请同时在服务器自身防火墙上也严格遵守。
例外就是申请的访问策略要和实际的一致，不允许授权做接口使用，实际开放出数据库端口来。

* 运行应用的账号权限过高
描述：直接使用root账号运行接口的jar包启动web服务
解决办法：使用普通账号来运行服务

* 敏感端口的暴露
描述：将3306、3389等敏感且不应该暴露的端口直接暴露在互联网上
解决办法：在防火墙上加上策略，禁止访问或者只允许白名单IP做访问；只开放必须的比如接口和前端的端口。

* 中间件的维护页面暴露
描述：Elasticsearch等中间件会暴露管理维护页面或者接口
解决办法：及时关闭、限制内网访问、限制白名单ip访问

* 第三方组件的维护页面或者端口暴露
描述：应用开发中，会使用druid、swagger等管理工具完成一些接口开放或者数据库维护的目的，而这些往往不需要授权即可访问
解决办法：对上述接口或者页面加入授权、在生成环境关闭

* 缺少会话超时机制
描述：会话超过10分钟还是继续保持
解决办法：在nginx等中间件，增加会话超时时间的设置

### 应用层面
应用层面指的业务应用开发中，和业务功能相关的可能出现的安全漏洞，其中验证码、登录、文件是重灾区，也是安全漏扫重点排查的地方，需要格外小心

* 图形验证码生命周期(验证码复用)
描述：在登录过程需要有图形验证码，而验证码在请求完成(成功或失败)后没有及时失效；或者是验证码的有效期太长，一直没有失效
解决办法：验证码生成后，将验证码uuid和内容存入缓存或数据库中，并设定失效时间；并且在每次带验证码uuid的请求完成后，无论请求成功还是失败，都将对应的记录删除或失效。

* 短信验证码生命周期(验证码复用)
描述：在使用手机号+短信验证码登过程中，登录完成后，验证码还可以继续用来登录；或者是验证码的有效期太长，一直没有失效
解决办法：验证码生成后，将短信验证码内容存入缓存或数据库中，并设定失效时间；并且在登录完成后，将短信验证码的记录删除或失效。
 
* 敏感信息明文传输
描述：对于密码、个人身份信息(身份证号)、交易信息等敏感数据，在前后端交互过程中，直接传输了。
解决办法：不建议明文传输，原先的要求是传输加上ssl(也就是使用https协议)可算符合，后续也陆续提高要求不再允许。将敏感信息用AES等对称加密方法做加密，可以针对敏感信息单独加密，也可以将整个请求做加密。注意建议用AES，md5是不允许的。具体见AuthController中的login。

* 弱密码
描述：用户的的登录密码不符合强密码的策略，有可能会被暴力穷举扫描出来，比如admin、123456、111111等
解决办法：对于用户的初始登录密码，以及密码修改时候的新密码，做密码强度的校验，比如满足强密码的规则，建议密码规则为:8-20个字符，且包含字母，数字和特殊字符。  
注意其它如修改用户也会涉及用户密码的修改，容易被忽略。

* 暴力穷举账号或密码
描述：账号密码登录时，登录失败信息过于明确，比如提示用户不存在，会存在暴力穷举账号的问题
解决办法1：登录失败一律提示用户名或者密码错误，而不给过于明确的错误信息
解决办法2：登录请求都需要加上图形验证码
解决办法3：登录失败次数过多，将账号做锁定(可以是锁定让管理员解锁，也可以是一定时间内不允许登录)

* 缺少验证码机制(同暴力穷举账号或密码)
解决办法：登录、发送登录验证码等无需授权的敏感接口加上图形验证码做验证

* 缺少账号锁定机制(同暴力穷举账号或密码)
描述：账号密码登录，密码错误次数超过一定次数后，还允许登录。
解决办法：账号密码登录，短时间内密码连续输入错误5次，就锁定账号(需管理员解锁)或者30分钟内锁定不允许登录(30分钟后自动解锁)

* 缺少密码找回机制
描述：从功能层面，如果业务系统是账号密码登录的，在登录页面缺少密码找回的入口
解决办法：在登录页面，添加找回密码的入口，可以是用其它辅助信息(如短信验证码、邮箱等)重置密码，或者不实现功能只给一个提示：请联系管理员重置密码。

* 横向(数据权限)越权漏洞
描述：横向指的是访问到了不该访问到的数据，比如财务部的用户业务限制只能查看到财务部的数据，而实际财务部账号访问到了技术部的数据。
解决办法：在业务代码层面，做严格控制，不要为了偷懒返回所有数据让前端挑选。

* 纵向(功能权限)越权漏洞
描述：纵向指的访问到了没有权限的功能，比如普通员工没有数据编辑权限，而实际访问到了数据编辑的接口
解决办法：借助shiro，在接口层面使用@RequirePermission或者@RequireRole来实现接口的访问控制，具体见[用户权限控制](./boot/uc_rbac.md)

* 账号密码等敏感信息在配置文件中明文存储
描述：账号密码等敏感信息在配置文件中明文存储
解决办法：做非对称加密处理

* 文件上传未做文件类型限制
描述：在文件上传接口中，未对上传文件的文件类型做限制
解决办法：在前后端都做一层校验，只有符合业务需求的文件类型(简单做可使用后缀名)才允许上传

* 用户注销后，用户授权信息未失效
描述：用户主动退出后，前端虽然将token从前端删除了，但token还是有效的，任然可以用来访问接口
解决办法：用户主动退出后，需要调用接口将token做注销处理(从缓存或者数据库删除或者置为失效)
ps. 这也是为什么单纯的jwt在实际的业务系统中很难使用的一个原因。

* 未授权访问
描述：访问接口的时候，未带token或者带有伪造(过期)token，接口任然可以访问到
解决办法：除登录、图形验证码、发送短信验证码等从业务上必须就是未登录前请求的接口，其它所有接口一律过授权校验。

* 敏感数据暴露
描述：敏感信息包括手机号、密码、头像(可能会是用户的照片)、身份证号码、住址等，在前端直接显示了，或者前端做了mask，但接口实际将所有数据都返回了
解决办法：控制最小返回机制，非必要信息不做返回，并且对返回第信息做必要的mask处理，有需要的时候，再返回完整信息
